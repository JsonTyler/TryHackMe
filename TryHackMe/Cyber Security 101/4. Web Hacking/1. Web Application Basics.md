- HTTP Messages
	- HTTP message are just packets of data that are exchanged between the client and web server
		- Show users' requests and the server's responses
	- Two types
		- **HTTP Requests**: Sent by the user to trigger actions on the web application.
		- **HTTP Responses**: Sent by the server in response to the user’s request.
	- Anatomy of a HTTP Message
		- Start Line: 
			- introduction of message and tells you what kind of message is being sent and how it should be handled
		- Header: 
			- made up of key-value pairs that provide extra information about the HTTP message. They give instructions to the client/server handling the request/response. Headers can cover security/content types/etc.
		- Empty Line: 
			- A divider that separates the header & body for clarity of communication
		- Body:
			- Where the actual data is stored
	- Why Understanding HTTP Messages Matters
		- These messages are the foundation of how web applications communicate. If they’re structured properly, everything works smoothly.
		- Knowing how they work will help you diagnose issues in web communication, which means better performance and reliability for your web application.
		- It’s also crucial for security. Understanding HTTP messages helps you implement strong security measures to protect data during transmission.
- HTTP Request: Request Line & Methods
	- Definition
		- An HTTP request is essentially what a user sends to a web server to interact with a web app
		- ![[Pasted image 20261003183131.png|306]]
	- Request Line:
		- First part of an HTTP request and tells the server the kind of request
		- 3 main parts:
			- HTTP method
			- URL path
			- HTTP version
	- Http Methods
		- Tells the server what kind of action you want to perfom on the resource identified by the URL path
		- GET, POST, PUT, DELETE, PATCH, HEAD, OPTIONS, TRACE, CONNECTION
		- Each of the above methods has it's own set of security rules
	- URL Path
		- Tells the server where to find the resource it's asking for
		- Common for attackers to try and manipulate the URL path to exploit vulnerabilityies
		- Important to:
			- Validate the URL path to prevent unauthorised access
			- Sanitise the path to avoid injection attacks
			- Protect sensitive data by conducting privacy and risk assessments
	- HTTP Version
		- Shows the protocol version used to communicate between the client & server
			- **HTTP/0.9** (1991)The first version, only supported GET requests.
			- **HTTP/1.0** (1996)Added headers and better support for different types of content, improving caching.
			- **HTTP/1.1** (1997): Brought persistent connections, chunked transfer encoding, and better caching. It’s still widely used today.
			- **HTTP/2** (2015): Introduced features like multiplexing, header compression, and prioritisation for faster performance.
			- **HTTP/3** (2022): Built on HTTP/2, but uses a new protocol (QUIC) for quicker and more secure connections
		- HTTP/2 & HTTP/3 offer better speed & security but many systems still use HTTP/1.1 because it's well supported and works in most setups
- HTTP Request: Headers & Body
	- Request Headers
		- They allow extra info to be sent to the web server
		- Common Request Headers
			- Host: Specifies the name of the web server the request is for.
			- User-Agent: Shares information about the web browser the request is coming from.
			- Referer: Indicates the URL from which the request came from.
			- Cookie: Information the web server previously asked the web browser to store is held in cookies.
			- Content-Type: Describes what type or format of data is in the request.
	- Request Body
		- The data is located inside the HTTP Request Body (POST/PUT)
		- Formatting of data can take many forms: URL Encoded, Form Data, JSON, XML
			- **URL Encoded (application/x-www-form-urlencoded)**: A format where data is structured in pairs of key and value where (`key=value`). Multiple pairs are separated by an (`&`) symbol, such as `key1=value1&key2=value2`. Special characters are percent-encoded.
			- **Form Data (multipart/form-data)**: Allows multiple data blocks to be sent where each block is separated by a boundary string. The boundary string is the defined header of the request itself. This type of formatting can be used to send binary data, such as when uploading files or images to a web server.
			- **JSON (application/json)**: In this format, the data can be sent using the JSON (JavaScript Object Notation) structure. Data is formatted in pairs of name : value. Multiple pairs are separated by commas, all contained within curly braces { }.
			- **XML (application/xml)**: In XML formatting, data is structured inside labels called tags, which have an opening and closing. These labels can be nested within each other. Y
- HTTP Response: Status Line & Status Codes
	- Backgounrd
		- When interacting with a web app, the server sends back an HTTP response to let you know sttatus
			- They included a **status code** and a short explanation (**Reaseon Phrase**) that explains how the server handled your request
	- Status Line
		- The first line in every HTTP response
		- Gives 3 pieces of info:
			1. **HTTP Version**: This tells you which version of HTTP is being used.
			2. **Status Code**: A three-digit number showing the outcome of your request.
			3. **Reason Phrase**: A short message explaining the status code in human-readable terms.
	- Status Codes & Reason Phrases
		- Status Code: number that tells you if the request succeeded or failed
		- Reason Phrase: explains what happened
		- **Informational Responses (100-199)** : These codes mean the server has received part of the request and is waiting for the rest. It’s a "keep going" signal.
		- **Successful Responses (200-299)**: These codes mean everything worked as expected. The server processed the request and sent back the requested data.
		- **Redirection Messages (300-399)**: These codes tell you that the resource you requested has moved to a different location, usually providing the new URL.
		- **Client Error Responses (400-499)**: These codes indicate a problem with the request. Maybe the URL is wrong, or you’re missing some required info, like authentication.
		- **Server Error Responses (500-599)**: These codes mean the server encountered an error while trying to fulfil the request. These are usually server-side issues and not the client’s fault.
	- Common Status Codes
		- 100 (Continue)
		- 200 (OK)
		- 301 (Moved Permanently)
		- 404 (Not Found)
		- 500 (Internal Server Error)
- HTTP Response: Headers & Body
	- Response Headers
		- A Response Header happens when a web server responds to an HTTP request
			- Generally key-value pairs
			- Provide important info about the response and tell the client/browser how to handle it
	- Required Response Headers
		- Date: Shows exact date/time when the response was generated by the server
		- Content-Type: Tells the client what kind of content it's getting and the character set to help the browser display it properly
		- Server: Shows what kind of server software is handling the request (good for debugging but can be targeted by attackers so sometimes hidden)
	- Other Common Response Headers
		- Set-Cookie: Sends cookies from the server to the client, which the client then stores and sends back with future requests. Cookies should be set with HttpOnly flag (so they can't be accessed by JS) and the Secure flag (so they're only sent over HTTPS)
		- Cache-Control: Tells the client how long it can cache the response before checking with the server again.
		- Location: Used for re-direction purposes. It tells the client where to go next if the resource has moved.
	- Response Body
		- The HTTP response body is where the data lives
		- To prevent injection attacks like XSS always sanitise and escape any data before including it in response
- Security Headers
	- Background
		- HTTP Security Headers help improve the overall security of web apps by mitigating against various attacks (XSS, clickjacking, etc)
		- Resource to analyze the security headers of any website: https://securityheaders.io/
	- Content-Security-Policy (CSP)
		- A header that is an additional security layer that can help mitigate against attacks (XSS)
		- Provides a way for admins to say what domains/source are considered say
		- Ex: `Content-Security-Policy: default-src 'self'; script-src 'self' https://cdn.tryhackme.com; style-src 'self'`
		- Some headers:
			- default-src: specifies the default policy of self, which means only the current website
			- script-src: specifies the policy for where scripts can be loaded from
			- style-src: specifies the policy for where style CSS style sheets can be loaded from
	- Strict-Transport-Security (HSTS)
		- Ensures that web browsers will always connect over HTTPS
		- Ex: `Strict-Transport-Security: max-age=63072000; includeSubDomains; preload`
	- X-Content-Type-Options
		- Used to instruct browsers to to guess the MIME type of a resource but only use the Content-Type header
		- Ex: `X-Content-Type-Options: nosniff`
	- Referrer-Policy
		- This header controls the amount of info sent to the desintaiton web server when a user is re-directed (ex: when they click a hyperlink)

			- no-referrer: completely disables any info being sent about the referrer
			- same-origin: only sends referrer info when the destination is part of the same origin
			- strict-origin: only sends the referrer as the origin when the protocol stays the same (Ex: HTTPS -> HTTPS)
			- strict-origin -when-cross-origin: same as strict-origin but for same-origin requests it sends the full URL path in the origin header
