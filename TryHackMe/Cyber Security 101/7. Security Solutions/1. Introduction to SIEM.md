- Introduction
	- Background
		- SIEM stands for "Security Informaiton & Event Management system"
			- It is the core security solution that a SOC analyst uses in the security operations center
- Logs Everywhere
	- Logs are often generated continuously and serve as a trail of all the activities
	- Different categories of logs
		- Host-Centric Log Sources
			- These log sources capture events that occurred within or related to the host. Devices that generate host-centric logs include Windows, Linux, servers, etc.
			- Examples:
				- User accessing a file
				- User attempting to authenticate
				- Powershell execution
		- Network-Centric Log Sources
			- Network-related logs are generated when the hosts communicate with each other or access the internet to visit a website. Devices that generate network-centric logs are firewalls, /, routers, etc.
			- Examples:
				- SSH connection
				- Web traffic
				- A user accessing the company's resource through VPN
	- Answers Nowhere
		- Issues:
			- **Too many log sources** — Networks generate huge amounts of logs across many devices, making manual review time-consuming.
			- **No centralization** — Logs are stored on individual machines, requiring analysts to connect to each system separately.
			- **Limited context** — A single log may look harmless, but correlating logs across systems can reveal an attack, such as lateral movement.
			- **Too much data to analyze** — Humans cannot realistically review hundreds of events per second without missing important activity.
			- **Different formats** — Each log source may use a different format, making analysis more difficult.
- Why SIEM
	- Background
		- SIEM stands for "Security Information and Event Management"
		- It is a security solution that collects logs from various types of log sources, standardizes their format into a consistent format, correlates them, and detects malicious activities via detection rules

- Log Sources & Ingestion
	- Log Sources
		- Every device in network generates some type of log
	- Windows Machine
		- Records every event that can be viewed via the "Event Viewer"
	- Linux Machine
		- Common log locations
			- /var/log/httpd: Contains HTTP Request  / Response and error logs.
			- /var/log/cron: Events related to cron jobs are stored in this location.
			- /var/log/auth.log and /var/log/secure: Stores authentication-related logs.
			- /var/log/kern: This file stores kernel-related events.
	- Web Server
		- Logs of requests/responses coming in and out of web server
			- In Linux this is apache related logs in `/var/log/apache` or `/var/log/httpd`
	- Log Ingestion
		- Each SIEM solution has its own way of ingesting logs
		- Some examples of common methods for ingesetion
			- - **Agent / Forwarder** — A lightweight program installed on endpoints that collects important logs and sends them to the SIEM server.
			- **Syslog** — A common protocol that collects logs from systems like web servers and databases and sends them to a centralized location in real time.
			- **Manual Upload** — Some SIEMs allow analysts to upload existing/offline log data for analysis. The SIEM then normalizes the data.
			- **Port Forwarding** — The SIEM listens on a specific port, and endpoints send their log data to that port.
- Alerting Process & Analysis
-  SIEM Detection Rules & Alerts
	- **Detection rules** = logical conditions that identify suspicious activity and trigger alerts.
	- Rules look for specific **field + value combinations** in normalized logs.
	- Examples:
	    - 5 failed logins in 10 sec → multiple failed login alert
	    - Successful login after failures → suspicious login
	    - USB plugged in → USB alert
	    - Outbound traffic > 25 MB → possible data exfiltration
	- **Event ID 104 + WinEventLog** → Event Log Cleared
	- **Event ID 4688 + `whoami`** → WHOAMI command execution
	- **Alert investigation:**
	    1. Examine related events.
	    2. Check which rule conditions triggered.
	    3. Determine **true vs. false positive**.
	    4. False positive → tune rule.
	    5. True positive → investigate/respond.
	- Possible responses: contact asset owner, isolate infected host, block suspicious IP.
	- **Flow:** `Logs → Detection Rules → Alert → Investigation → Response`
