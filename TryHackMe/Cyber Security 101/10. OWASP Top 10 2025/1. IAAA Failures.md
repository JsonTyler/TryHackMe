- What is IAAAA
	- It is a simple way to think about how useres and their actions are verified on applications
	- The four items are:
		- **Identity** - the unique account (e.g., user ID/email) that represents a person or service.
		- **Authentication** - proving that identity (passwords, OTP, passkeys).
		- **Authorisation** - what that identity is allowed to do.
		- **Accountability** - recording and alerting on who did what, when, and from where.
- A01: Broken Access Control
	- Main idea: 
		- Enforce server-side checks on **every** request
	- This happens when the server doesn't properly enforce **who can access what** on every request
	- A common example of this is IDOR (Insecure Direct Object Reference)
		- This would mean changing an id lets you see/edit someone else's data
	- Horizontal: Can see/edit other users but no role elevation
	- Vertical: Can see/edit and role elevation
- A07: Authentication Failures
	- Main idea:
		- Enforce unique indexes on the canonical form, rate-limit/lock out brute force, and rotate sessions on password/privilege changes.
	- This happens when an application can't reliably verify/bind a user's identity
	- Common issues:
		- username enumeration
		- weak/guessable passwords (no lockout/rate limits)
		- logic flaws in the login/registration flow
		- insecure session or cookie handling
- A09: Logging & Alerting Failures
	- Main idea:
		- Log the full auth lifecycle (fail/success, password/2FA/role changes, admin actions), centralise logs off-host with retention, and alert on anomalies (e.g., brute-force bursts, privilege elevation).
	- This happens when applications don't record or alert on security-relevant events so defenders can't detect or investigate attacks
